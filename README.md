# zeiban（税番）

日本語 | [English](README.en.md)

商品の文（品名・素材・説明）から、米国の関税率表（HTS）の 10 桁の番号を出す小さなモデル。CPU だけで動き、実行時に LLM もネットワークも使わない。

- **小さい**: 配る一式は 55.1 MB、常駐メモリは最大 約 76 MB、1 件 0.07〜0.33 秒（CPU 2 スレッド。[速さと大きさ](#速さと大きさ)）。
- **答えの形**: 10 桁のコード・確度・代わりの候補・基本の税率に、**確認の質問**（「外側は織物か、綿か」のように、候補が分かれる所を関税率表の公式の文で聞く）を付けて返す。
- **改訂に付いていく仕組み**: 関税率表の版を毎日見張り、版ごとの写しと差分を残している。モデルの中の表（木・行の文・税率）は重みではなくデータとして持つ。
- **英語と日本語**の商品文を受け付ける。多言語の読み手 1 つで読む（[日本語での評価](#日本語での評価)）。
- **動かし方は 3 つ**: Rust の実行ファイル（速い・小さい）、WebAssembly（Node・Bun・Deno・ブラウザの中で動く）、Python の実装。答えは同じ。
- **v0.3.0 で、文を読む層を入れ替えた。** どの入力でも、v0.2.x と答えが変わりうる（v0.2.x の「日本語でない入力の答えは v0.1.0 と変わらない」は、v0.3.0 には当てはまらない）。前の版の一式と実行ファイルは、リリースに残してある。

> **先行公開: `v0.4.0-rc1`（開発途中の試用版）**
>
> 本番向け（`v0.4.0`）の再学習・Stage-2 再順位付け器の統合が終わるまでの繋ぎとして、**24 層混合 2/4-bit の Stage-1 単体版（`b32`, `avx2_int8_k64`）** を `v0.4.0-rc1` ブランチ・GitHub Pre-release・Hugging Face リビジョン `v0.4.0-rc1` 向けに用意した。封印テストセットは `v0.4.0` の確定評価まで開けていないため、以下は開発用・校正用の実測値のみを示す。

> - **v0.3.0 は、テスト用の品での質問なしの精度が、v0.2.1 とほぼ同じだった**（1 回だけ採点した。2026-11-18。[テスト用での結果](#テスト用での結果)）。伸びたのは、学習よりあとに出た判例（品名＋説明の 10 桁 27% → 39%）と、質問に答える流れ。作り始める前に決めた目安のうち、通販の商品名の 10 桁（30% 以上）と、確度 0.9 以上の品の的中率（90% 以上）には届かなかった。
> - 日本語は、日本の税関の書き方の文（品名＋製法・成分などの概要）で、6 桁の 1 位が 56〜74%。品名だけ・品名＋概要では、v0.2.1 より 3〜5 ポイント低い。過去の回答に似た品が多いデータでの数で、似た文の無い品では 42〜65%。
> - v0.2.1 より遅い（1 件の時間が約 10 倍）。速さや、日本の税関の書き方の文が大事なら、v0.2.1 の一式を v0.3.0 の実行ファイルで使える（[2. 一式を取る](#2-一式を取る)）。
> - 通関の判断の代わりにはならない。税率は関税率表の基本の欄で、追加の関税は入っていない。

## 使い方

動かし方は 3 つある。入力と応答の形は同じで、答えも同じになる。

- **Rust の実行ファイル**（下の 1〜3）: 速くて小さい。Rust で組み立てる。
- **WebAssembly**（[下の節](#webassembly-で使う)）: 組み立てが要らない。JavaScript の実行環境の中で、別のプロセスなしに動く。
- **Python**（[下の節](#python-で使う)）: 組み立てが要らない。同じ計算を、torch と numpy でする。

### 1. 実行ファイルを作る

Rust が要る（1.91 で確かめた）。

```sh
git clone https://github.com/ikenokazuki/zeiban.git
cd zeiban/rs
cargo build --release
```

できるのは `rs/target/release/zeiban`（約 0.8 MB）。x86-64 の Linux で確かめた。AVX2 のある CPU では専用の計算を使い、無い CPU では素の Rust の計算に自動で切り替わる。ARM64 は、動く作りにはしてあるが、実機ではまだ確かめていない。

### 2. 一式を取る

重み・関税率表の木・索引などを 1 つにまとめたファイル（一式）と、その目録を、同じフォルダに置く。

```sh
mkdir -p ../bundle && cd ../bundle
curl -LO https://github.com/ikenokazuki/zeiban/releases/download/v0.3.0/zeiban.bin
curl -LO https://github.com/ikenokazuki/zeiban/releases/download/v0.3.0/zeiban.json
echo "5413a838519cb1cf2d27ea4c9043e37d84aef5dcb85735da28628db9dbd919f1  zeiban.bin" | sha256sum -c
```

前の版（v0.1.0〜v0.2.1）の一式と実行ファイルも、リリースに残してある。v0.3.0 の実行ファイルは、v0.2.x の一式も読める（コード・確度・税率は v0.2.x と同じで、質問の作りだけが新しくなる）。 v0.2.1 の一式（61.0 MB。1 件 6〜36 ms）を使うときは、上の URL の `v0.3.0` を `v0.2.1` に替える（`zeiban.bin` の sha256 は `ba2f7883e9d37315c2c64137bd3fbe8d420eb0d552aa9e808b6e43b78a9653e0`）。

### 3. 動かす

標準入力に 1 行 1 件の JSON を渡すと、標準出力に 1 行 1 件の JSON が返る。

```sh
echo '{"name": "Womens tote bag"}' | ../rs/target/release/zeiban .
```

日本語の文も、同じように渡せる（同じ読み手が読む）。

```sh
echo '{"name": "メンズ 半袖 Tシャツ", "material": "綿100% ニット"}' | ../rs/target/release/zeiban .
```

入力の欄:

| 欄 | 中身 |
|---|---|
| `name` | 品名（必須） |
| `material` | 素材（任意） |
| `categories` | 店の付けた分類。文か、文の並び（任意） |
| `description` | 説明（任意） |
| `prefix` | もう分かっている頭の桁。2・4・6・8・10 桁の数字（任意。下の「質問と呼び直し」） |
| `confirm` | `true` にすると、確度が高い段も飛ばさずに、頭の桁から質問する（任意。下の「質問と呼び直し」） |

素材や分類は、説明の中に書くより、`material`・`categories` の欄で渡すほうがよく効く（品名のすぐ後に置かれるため）。入力は 256 トークンで切る。

応答（上のトートバッグの例。見やすく整えて、長い文は「…」で省き、代わりの候補は 1 件・選択肢は 15 個のうち 3 個だけ載せた）:

```json
{
  "hsCode": {
    "code": "4202924500",
    "description": "ARTICLES OF LEATHER; … > Trunks, suitcases, … > Other: > With outer surface of sheeting of plastics or of textile materials: > Travel, sports and similar bags: > Other (other than: With outer surface of textile materials)"
  },
  "sixDigit": "420292",
  "confidenceScore": 0.56,
  "sixDigitConfidence": 0.81,
  "dutyRate": {
    "general": "20%",
    "special": "Free (A,AU,BH,CL,CO,D,IL, JO,KR,MA,NP,OM,P,PA,PE,R,S, SG) 17.5% (E)",
    "other": "45%"
  },
  "alternates": [
    {"code": "4202923131", "description": "… > With outer surface of textile materials: > Of man-made fibers > Other (670)", "probabilityMass": 0.201, "dutyRate": {"general": "17.6%", "special": "…", "other": "65%"}}
  ],
  "questions": [
    {
      "digits": 8,
      "ask": true,
      "confidence": 0.57,
      "options": [
        {"prefix": "42029245", "label": "Travel, sports and similar bags: > Other (other than: With outer surface of textile materials)", "code": "4202924500", "probabilityMass": 0.466, "dutyRate": {"general": "20%", "special": "…", "other": "45%"}},
        {"prefix": "42029231", "label": "Travel, sports and similar bags: > With outer surface of textile materials: > Of man-made fibers", "code": "4202923131", "probabilityMass": 0.182, "dutyRate": {"general": "17.6%", "special": "…", "other": "65%"}},
        {"prefix": "42029215", "label": "Travel, sports and similar bags: > With outer surface of textile materials: > Of vegetable fibers and not of pile or tufted construction: > Of cotton (369)", "code": "4202921500", "probabilityMass": 0.044, "dutyRate": {"general": "6.3%", "special": "…", "other": "40%"}}
      ]
    }
  ],
  "htsRelease": "2026HTSRev22"
}
```

応答の欄:

| 欄 | 中身 |
|---|---|
| `hsCode` | 1 位の 10 桁と、関税率表の道筋の文 |
| `sixDigit` | 1 位の頭 6 桁（HS の国際共通の部分） |
| `confidenceScore` | 1 位の 10 桁が正しい確率の見積もり（0〜1） |
| `sixDigitConfidence` | 1 位の 6 桁までが正しい確率の見積もり |
| `dutyRate` | 関税率表の税率の欄。`general`（一般）・`special`（特恵）・`other`（第 2 欄）。公式の文字のまま |
| `alternates` | 代わりの候補（4 件まで）。`probabilityMass` は、上位 5 件の中での割合 |
| `questions` | 候補が分かれる所の質問（0 か 1 個。下の「質問と呼び直し」） |
| `htsRelease` | この一式が使っている関税率表の版 |
| `codes`・`scores` | 上位 5 件の 10 桁と点（照合用） |
| `reader` | v0.2.x の一式を、日本語用の層で読んだときだけ `"ja"` が入る。v0.3.0 の一式では出ない |

実行ファイルの 2 つ目の引数に数を渡すと、上位の件数を変えられる（既定は 5）。

### 質問と呼び直し

品名だけでは決まらないとき、モデルは「どこで迷っているか」を質問として返す。

- `digits`: 質問の桁。上の例では 8 桁（外側の素材が、織物か、それ以外か。織物なら、綿か、化学繊維か）。
- `options`: 選択肢（30 個まで）。`label` は関税率表の公式の文、`code` は「これを選んだらこのコードになる」、`dutyRate` はそのときの税率。選択肢を見せるだけで、税率の違い（上の例では 20%・17.6%・6.3%）まで伝えられる。`probabilityMass` は、選択肢のもとになった候補の中での割合。
- `ask`: 聞いたほうがよいかの目安。その段までが正しい確率の見積もり（`confidence`）が 0.7 より低いと `true`。
- 答えをもらったら、選ばれた選択肢の `prefix` を付けて呼び直す。その下の行だけから選び直す。

```sh
echo '{"name": "Womens tote bag", "prefix": "42029215"}' | ../rs/target/release/zeiban .
```

これで 1 位は 4202921500（綿の織物のトートバッグ。税率 6.3%）に決まり、質問は出なくなる。

**どの段を聞くか**（v0.3.0 で作り直した）:

1. 頭の桁から順に見て、確度が 0.7 より低い最初の段を探す。確度の高い段は飛ばす（上の例は、6 桁までの確度が 0.81 なので、8 桁から聞く）。
2. その段より上が 1 位と同じ候補を、点の高い順に 30 件まで集める。その候補が分かれる最初の段を、質問にする。
3. どの段も確度が高いときは、上位 30 件が分かれる最初の段を、`ask` を `false` にして返す（聞かなくてよいが、念のために見せられる）。

v0.2.x までは、上位 5 件が分かれる最初の段を聞いていた。上位 5 件に正解の側が入っていないと、選択肢に正しい答えが無かった。候補を 30 件に広げ、確度の高い段を飛ばすことで、同じ回数の質問で届く正解が増えた（[質問に答えたときの伸び](#質問に答えたときの伸び)）。

入力に `"confirm": true` を足すと、確度の高い段も飛ばさずに、上位 30 件が分かれる最初の段から聞く（上の例では 6 桁。`ask` は `false`）。質問の回数は増えるが、モデルが自信を持って間違えている段も、人が確かめられる。

```sh
echo '{"name": "Womens tote bag", "confirm": true}' | ../rs/target/release/zeiban .
```

1 回の呼び出しで必ず答えが返り、実行ファイルは状態を持たない。質問は追加の欄なので、無視して 1 位だけを使ってもよい。

素材を最初から書けば、答えが変わる。上の例に `"material": "cotton canvas"` を足すと、1 位は 4202921500（税率 6.3%）になる（10 桁の確度は 0.68 で、8 桁の質問は `ask` が `true` のまま残る）。

### 確度と税率の読み方

- `confidenceScore`・`sixDigitConfidence` は、学習に使っていない行（判例に近い文とその書き直し）で合わせ込んだ値（[確度の当たり具合](#確度の当たり具合)）。
- `probabilityMass` は候補の中での割合で、正しい確率ではない。
- `dutyRate` は関税率表の基本の欄だけ。第 99 類の追加の関税（232 条・301 条など）・不当廉売の関税・脚注・数量の単位は入らない。**実際に払う額ではない。**

### ほかの仕組みに組み込むとき

実行ファイルは、入力を 1 行読むごとに 1 行返す。立てたままにして 1 行ずつ渡せば、読み込み（約 15 ms）は最初の 1 回で済む。HTTP の口は入っていないので、要るなら薄い包みを自分で付ける。

### WebAssembly で使う

実行ファイルと同じ計算を、WebAssembly（`zeiban.wasm`、約 0.5 MB）としても配っている。Node・Bun・Deno・ブラウザなど、WebAssembly を動かせる所で、そのプロセスの中で動く。外からの取り込みが無いモジュールなので、ファイルにも通信にも触れない（一式の中身は、呼び手が読んで渡す）。

```sh
# リポジトリの直下で。bundle/ は、上の「2. 一式を取る」で作ったもの
curl -LO https://github.com/ikenokazuki/zeiban/releases/download/v0.3.0/zeiban.wasm
echo "d891a0e8caf2f1ad44c4d7053ccd498eb9c608506bd1099d44354cd9b1cb1434  zeiban.wasm" | sha256sum -c

echo '{"name": "Womens tote bag"}' | node js/zeiban.mjs zeiban.wasm bundle
```

JavaScript のコードから（`js/zeiban.mjs` は、依存の無い小さな包み）:

```js
import { readFileSync } from 'node:fs';
import { load } from './js/zeiban.mjs';

const z = await load(readFileSync('zeiban.wasm'), readFileSync('bundle/zeiban.json'), readFileSync('bundle/zeiban.bin'));
const r = z.classify({ name: 'Womens tote bag', material: 'cotton canvas' });
console.log(r.hsCode.code, r.sixDigit, r.dutyRate.general);   // 4202921500 420292 6.3%
```

- 答えは、Rust の実行ファイルと同じになる。467 件（質問に答えたあとの呼び直しを含む）で比べて、上位 5 件のコードと順・確度・質問・税率が全部同じだった（点の差は最大 0.0002）。Bun 1.3 と Node 22 で確かめた。
- 速さは、1 スレッドで、ふつうの長さの入力が 1 件 平均 約 0.5〜0.6 秒、いちばん長い入力（256 トークン）が 1 件 約 1.0〜1.2 秒。実行ファイル（2 スレッド・専用の計算）より遅い。一式の 55 MB は、wasm のメモリの中に置かれる。
- 自分で作るときは `rs/build-wasm.sh`（Rust の `wasm32-unknown-unknown` と、LLVM の `wasm-ld` が要る）。台本がパスを決まった名前に置き換えるので、組み立てる場所が違っても、同じソースからは同じ中身のファイルができる（Rust 1.91.1・LLD 21.1.7。道具の版が違えば、中身は変わりうる）。
- ほかの言語から直に呼ぶときの口は 6 つ（`zb_alloc`・`zb_free`・`zb_load`・`zb_classify`・`zb_out_ptr`・`zb_out_len`）。呼ぶ順は、`rs/src/main.rs` の `mod wasm` の前の注釈にある。

### Python で使う

`py/zeiban.py` は、同じ一式を読む Python の実装。6 層の読み手を torch で、残り（語の一致の点・木の採点・確度・質問）を numpy で計算する。入力と応答は、Rust の実行ファイルと同じ。語の区切りの定義（`tokenizer.json`・`bmx-tokenizer.json`）を、一式と同じフォルダに置く。

```sh
pip install numpy torch tokenizers

# リポジトリの直下で。bundle/ は、上の「2. 一式を取る」で作ったもの
curl -L -o bundle/tokenizer.json https://github.com/ikenokazuki/zeiban/releases/download/v0.3.0/tokenizer.json
curl -L -o bundle/bmx-tokenizer.json https://github.com/ikenokazuki/zeiban/releases/download/v0.3.0/bmx-tokenizer.json

echo '{"name": "Womens tote bag"}' | python3 py/zeiban.py bundle
```

Python のコードから:

```python
import sys
sys.path.insert(0, 'py')
from zeiban import Zeiban

z = Zeiban('bundle')
r = z.classify({'name': 'Womens tote bag', 'material': 'cotton canvas'})
print(r['hsCode']['code'], r['sixDigit'], r['dutyRate']['general'])   # 4202921500 420292 6.3%
```

- 答えは、Rust の実行ファイルと同じになる。3,805 件（質問に答えたあとの呼び直しを含む）で比べて、上位 5 件のコードと順・確度・質問・税率が全部同じだった（点の差は最大 0.0004）。実行ファイルの 2 つの計算（AVX2・素の Rust）の両方で確かめた。
- 速さは、短い入力で 1 件 約 50 ms（中央値。同じ台・2 スレッド）。読み込みに約 3 秒かかり、メモリは約 650 MB 使う（torch の分）。軽さが要るなら、Rust の実行ファイルを使う。

- v0.2.x の一式は、これまでどおり、エンコーダのフォルダ（リリースの `zeiban-encoder.tar.gz`）を 2 つ目の引数に渡して読む（`Zeiban('bundle', 'zeiban-encoder')`。transformers が要る）。v0.3.0 の一式には、別に配るエンコーダは無い。

### 質問に答えたときの伸び

- **聞く目安に従う**: `ask` が `true` の質問にだけ答える。
- **いつも答える**: 質問が出るかぎり答える。

## 速さと大きさ

配る一式（v0.3.0）で測った。CPU は AMD EPYC（Milan）の仮想マシンで、計算は 2 スレッド。ほかの仕事も動いている台での数。

| 256 トークンの入力の中央値・95% 点 | 295 ms・324 ms | 616 ms・658 ms |
| 読み込み（1 件目を受けられるまで） | 約 15〜30 ms | 約 15〜30 ms |
| 常駐メモリの最大 | 75.6 MB | 75.0 MB |

| 一式の中身 | MB |
|---|---|
| 読み手の 6 層（4 ビット） | 16.5 |
| 読み手の語の埋め込み（4 ビット） | 12.8 |
| 語の一致の索引（BMX） | 12.3 |
| 節のベクトル（4 ビット） | 5.1 |
| 関税率表の行の文・木・税率 | 2.7 |
| 語の一致用の語の区切りの表・NFKC の表 | 2.4 |
| 読み手の語の区切りの表（BPE） | 1.9 |
| 読み手のほかの部品（層ごとの補助の表・射影） | 1.5 |
| **合計** | **55.1** |

- **v0.2.1 より遅い。** v0.2.1 は 1 件 6〜36 ms だった。読み手が 3 層・幅 256 から 6 層・幅 512 になった分で、約 10 倍かかる。作り始める前に決めた目安（1 件 1 秒以下）には収まる。
- 常駐メモリの最大は 約 76 MB（作り始める前の目安は 80 MB）。一式はメモリにマップして読むので、そのうち 55 MB はファイルの写し。残りは、実行ファイルが自分で持つ表と、いちばん長い入力を読むときの作業用の配列。
- 1 件の時間には、語の区切り・索引の検索・読み手・採点・上位 5 件の取り出しまでの全部が入る（JSON の読み書きは入らない）。入力が長いほど時間がかかる（256 トークンで切る）。
- WebAssembly は 1 スレッドで動くので遅い。ふつうの長さの入力で平均 約 0.5〜0.6 秒、いちばん長い入力（256 トークン）では 1 件 1.0〜1.2 秒かかる（[WebAssembly で使う](#webassembly-で使う)）。
- Python の実装は、短い入力で 1 件 約 50 ms・読み込み 約 3 秒・メモリ 約 650 MB（[Python で使う](#python-で使う)）。
- v0.2.1 の一式は 61.0 MB・常駐 78 MB、v0.1.0 は 57.5 MB・常駐 74 MB だった。

## モデルの作り

```
商品の文（品名・素材・分類・説明）
   │
   ├─(1) 語の一致の道 ─ BMX の索引（葉 19,926 個の文書）─→ 上位 64 個の葉と点
   │
   └─(2) 意味の道 ─ 語の区切り（BPE。最大 256 トークン）
                    → 6 層の読み手（幅 512）→ 全トークンの平均を 768 次元に写した状態 h
                    → 5 段の問いのベクトル q_t（2・4・6・8・10 桁）
                    → 節のベクトル e_t との cos
   ▼
(3) 段ごとの点   s_t = scale_t × cos(q_t, e_t) + λ_t × BMX_t
(4) 葉の点       = 5 段の log softmax(s_t) を、その葉の道筋に沿って足したもの
   ▼
上位 5 件の 10 桁 → 確度・質問・税率を付けて返す
```

関税率表は、類（2 桁）→ 項（4 桁）→ 号（6 桁）→ 8 桁 → 10 桁の木になっている。ここでは、木の分かれ目を「節」、一番下の 10 桁の行を「葉」と呼ぶ。木を 1 段ずつ下りるのではなく、5 段を 1 回で採点して、道筋の点の合計で葉を選ぶ。上の段で間違えても、下の段の点が強ければ取り戻せる。

| 部品 | 中身 |
|---|---|
| 読み手 | `google/embeddinggemma-2`（文の層は 24 層）の、先頭の 6 層。幅 512・注意の頭 4・中間 2,048。層 0〜4 は近くだけを見る注意、層 5 は全体を見る注意。文の頭に `task: classification | query: ` を付けて読む |
| 語の埋め込み | 語彙 49,106 × 幅 512（土台の語彙 262,144 から、学習の文によく出る語と、1 字・1 バイトの語だけを残した） |
| 問いの射影 | 段ごとの線形 768 → 256 が 5 つ |
| 節のベクトル | 木の節 38,276 個（段ごとに 96・1,228・5,612・11,414・19,926）× 幅 256。先に計算して配る |
| 語の一致の索引 | 葉ごとの文書（関税率表の道筋の文＋その葉の学習の文）を BMX で引く。v0.2.x と同じもの |

パラメータは合わせて 約 7,000 万個（語の埋め込み 2,510 万・6 層 約 3,300 万・節のベクトル 980 万・ほか 約 300 万）。重みは 4 ビット（−7〜7 の整数に、行ごとの倍率を掛ける形）で配る。

- **読み手**: 土台は、Google DeepMind の多言語の埋め込みモデル `google/embeddinggemma-2`（Apache-2.0）。文を読む 24 層のうち、先頭の 6 層だけを取り出して、関税率表の分類に合わせて学習し直した。v0.2.x までの読み手（`cl-nagoya/ruri-v3-30m` から作った 3 層・幅 256）と入れ替えたもので、学習に使っていない新しい判例での 10 桁の 1 位は 0.280 → 0.419 に上がった（[精度](#精度)）。そのぶん、1 件の時間は約 10 倍になった（[速さと大きさ](#速さと大きさ)）。
- **4 ビットの重み**: 丸めない重みで学習したあと、4 ビットの丸めを入れたまま学習を続ける（丸めない自分の出力を先生にする）。配る値は、学習の最後の整数そのもの。新しい判例の 10 桁の 1 位は、丸めを入れる前が 0.397、丸めを入れた学習のあとが 0.416 で、丸めで下がってはいない。
- **語彙を絞る**: 土台の語彙 262,144 語のうち、49,106 語だけを持つ。残さなかった語は、より短い語の並びに分かれる（未知の語にはならない）。語彙を絞らない形と比べて、新しい判例の 10 桁は変わらず（+0.007 [−0.004, +0.017]）、通販の商品文での先生のラベルとの一致は −0.013 [−0.035, +0.007] だった（違いとは言えないが、英語の商品文だけで見ると −0.025）。
- **節のベクトル**: 3 層の読み手のときに作った節のベクトル（節の文をそのエンコーダで読んだベクトルに、節ごとに覚えるベクトルを足したもの）を始めの値にして、新しい読み手と一緒に学習し直した。
- **BMX**: BM25 に、語の情報量（エントロピー）の重みを足した語の一致の式（arXiv 2408.06643）。関税率表は「綿」「ニット」「ステンレス」のような語がそのまま決め手になるので、語の一致の点を意味の点に足す。語の一致の点だけで答えると、新しい判例の 10 桁の 1 位は 0.287（読み手と合わせて 0.419）。語の区切りは、v0.2.x と同じもの（`ruri-v3-30m` の語彙）を使う。
- **確度**: 段ごとに、上位の候補の中で 1 位と同じ節にいる候補の割合と、1 位の点から、ロジスティック回帰で「1 位のその段までが正しい確率」を出す。質問に答えたあとの呼び直しには、別に合わせた係数を使う。
- **質問**: 確度が足りない最初の段を探し、そこで候補（上位 30 件まで）を節ごとにまとめて選択肢にする（[質問と呼び直し](#質問と呼び直し)）。

### 日本語の文

v0.3.0 は、読み手が 1 つ。土台が多言語のモデルなので、日本語の文も同じ層で読む。

- v0.2.x の「かな・漢字が 1 割以上なら、日本語用の 2 つ目の層で読む」という切り替えは、無くなった。応答の `reader` の欄も出ない。
- 学習には、日本の税関の事前教示回答（6 桁までの正解）を足してある（[データの出どころと加工](#データの出どころと加工)）。
- 中国語などの文も、同じ読み手が読む。日本語と英語のほかの言語での精度は、測っていない。

### 加工

1. **関税率表から木を作る。** USITC の JSON の字下げを積んで、類 → 項 → 号 → 8 桁 → 10 桁の木にする。第 98・99 類（特別な規定・追加の関税）は当てる対象から外す。税率は、葉の行か、税率の書いてある一番近い上の行から引く。
2. **判例から作った問い（ATLAS）。** 問いの決まり文句を外して商品の説明にする。正解のコードが現行の版に無いときは、残っている一番深い桁までを正解にする。コードが複数ある判例は、どれも正解として扱う。
3. **判例の原文を商品文に書き直す。** 判例の原文には、照会した人の名前や住所が入っている。そこで、原文から LLM が「通販の題名の形の短い品名」と「商品の説明」を英語と日本語で書き、名前・住所・会社名は書かせず、正規表現でも消す。正解のコードは、原文の決まり文句からこちらで抜き出し、データセットに付いているコードと食い違うものは使わない。原文そのものは、学習にも一式にも入れていない。
4. **合成の商品名を書いて、確かめる。** 葉ごとに、道筋・となりの行・関係する注を LLM に見せ、決め手（素材・性別など）を入れた商品名を書かせる。書いた商品名は、別の呼び出しで「この葉と近い葉のどれか」を選ばせ、元の葉に戻らないものを捨てる。397,180 題のうち 350,251 題（88%）を採用した。書き手も確かめ役も同じ LLM なので、同じ思い違いは通り抜ける。
5. **通販の商品文にラベルを付ける。** 公開の商品文（題名・ブランド・分類・説明）を LLM に見せ、類 → 4 桁 → 6 桁 → 8 桁 → 10 桁と、段ごとに関税率表の選択肢から選ばせて、確率ごと記録する。**これは正解ではなく、先生の答え**（同じ先生の 10 桁の正解率は、開発用の通販の商品名で 52%）。そこで、確率の高い段までを固い正解にし、その先は確率で重みを付けて使う。
6. **漏れを防ぐ。**
   - ATLAS の検証用・テスト用と同じ判例らしい原文（コードが頭 8 桁で合い、語の重なりが大きいもの。1,720 件）は、書き直しから外した。
   - ATLAS のデータセットは、学習用と検証用・テスト用に、ほぼ同じ文の組がある（検証用 200 品のうち 66 品）。そこで、検証用は重複を除いた 134 品で読む。
   - LLM への依頼には、開発用の正解・テスト用の品・判例の原文を入れていない。
   - 測る前に、何を比べて、どうなったら採用するかを決めてから測った。
7. **日本の税関の回答（v0.2.0 から）。** 検索結果の一覧から、品名・概要・税番を取る。正解は、税番の頭 6 桁。登録番号で、学習 70%・開発用 10%・テスト用 20% に分ける（同じ登録番号の品は同じ側）。学習の行は 1 品につき 3 通り: 品名だけ・品名＋概要・事実だけ（概要から、税関の書いた頭の要約の文を外した、製法・原料・材質・用途などの並び）。LLM は使っていない。
8. **判例から抜き出した品名と説明（v0.3.0）。** 行ごとに「品名だけ」と「品名＋説明」の 2 通りの文にする。正解は、いまの木で解ける桁まで。次の行は、学習に入れない。
   - ATLAS の検証用・テスト用の品と同じ判例らしい行（11,684 行）。ATLAS には判例番号が無いので、コードの頭 8 桁が同じ行は文を見ずに外し、語の重なりでも外した。確かな組（23 組）は全部拾えたが、組が少ないので「漏れが無い」とまでは言えない。
   - 確度の合わせ込みに使う行と同じ判例らしい行（2,157 行）。
   - 2025-10-01 からの判例（2,997 行）。学習よりあとに出た判例として、評価用に取っておく。
   - 第 98・99 類のコードの行と、いまの木で 6 桁も解けない行（18,177 行）。
9. **英国の裁定（v0.3.0）。** 一覧から、品の説明と商品コードを取る。正解は、コードの頭 6 桁（6 桁までは国際共通）。説明の最初の文を品名の代わりにして、「品名だけ」と「品名＋説明」の 2 通りの文にする。5% は学習に入れずに取り分けた。LLM は使っていない。
10. **一式にまとめる。** 重みを 4 ビットにし、節のベクトル・索引・木・行の文・税率と一緒に 1 つのファイルにする。

### 配っていないもの

- 学習データそのもの（判例の書き直し・合成の商品名・ラベルを付けた商品文）と、学習・データ作りの台本は、このリポジトリに入れていない。入っているのは、実行ファイルのソース・Python の実装と、一式のファイル（リリースの添付）。
- 判例の原文と、要約の文は配らない。
- 日本の税関の回答・英国の裁定・公開の判例のデータの文も入れていない（出どころは上の表）。

## 改訂への追従

関税率表は、よく変わる。2025 年は 33 回、2026 年は 11 月半ばまでに 24 回、版が出た。古い判例のコードは、いまの表にもう無いことが多い（2000〜2025 年の判例 5.5 万件の 10 桁のうち、現行の版に残るのは 41%）。学習したコードを重みに焼き付けるだけのモデルは、表が変わるたびに古くなる。

### いま動いているもの

- **版の見張り**（`.github/workflows/watch.yml`、毎日）: USITC の版の一覧を見て、新しい版が出ていたら JSON を保存し、前の版との差分を作る。過去の版の JSON はあとから配布元で取れないので、取り逃がさないことに意味がある。
- **版の写しと差分**（`releases/`・`diffs/`）: 2025 年の基本版から現行までの 56 版と、となり合う 55 組の差分。
- **型分け**: 差分を 3 つの型に分け、商品の行が変わったとき（B・C）は issue を立てる。

  | 型 | 条件 | 55 組のうち |
  |---|---|---|
  | A | 商品の葉（第 1〜97 類）の増減が無く、文も変わらない | 44 |
  | B | 文の変化だけ、または葉の増減が 40 未満 | 8 |
  | C | 葉の増減が 40 以上 | 3 |

  行が大きく動くのは年 2 回（1 月と 7 月）で、多くは 1 つの行が数行に分かれる形。
- **正解の付け替え**（`hts/rev_remap.py`）: 古い版の 10 桁を、新しい版の木に付け替える。番号だけ替わった行は新しい番号へ、分かれた・まとめられた・消えた行は、残っている一番深い桁までに直す。2025 年の基本版から 2026 年の Rev23 までの 55 回を通すと、葉 19,708 のうち 19,525 が同じ 10 桁のまま、179 が 8 桁まで、4 が 6 桁までになる。
- **判例の取り消しの見張り**（`.github/workflows/bulletin.yml`、毎週）: 税関の週刊の公報から、判例の取り消し・変更の告示（判例番号・日付・代わりの判例・結論のコード）を抜き出す。判例の本文は残さない。

### モデルの側の備え

- 応答には、いつも表の版（`htsRelease`）が入る。
- 木・行の文・税率・索引は、重みではなくデータとして一式に入っている。行の文や税率だけが変わる改訂は、学習し直さずに一式を作り直せば済む作りにしてある。
- v0.2.x までの節のベクトルは、行の文をエンコーダで読んだ部分を持つので、増えた行にも文からベクトルを作れる。v0.3.0 の節のベクトルは、それを始めの値にして学習で動かしたもので、増えた行のベクトルを文から作る手順は、まだ確かめていない（増えた行は、語の一致の点だけで拾うことになる）。

### まだできていないこと

- いまの一式は 2026HTSRev22 で作った。現行の Rev23 は商品の行が同じ（型 A）なので、コードはそのまま通用する。**行が変わる版が出たときに一式を作り直す手順は、まだ自動になっていない。**
- 増えた行は、節ごとに覚えるベクトルが無い分だけ弱くなる見込み（覚えるベクトルを全部外すと、調整用の正解率が 0.56 → 0.45 に下がった。古い重みでの測り）。
- 改訂を再現した試験（葉の一部を「まだ無い行」として隠して学習し、あとで学習なしで足して当たるかを測る）は、計画だけで、まだ測っていない。「改訂に強い」と言える数字は、まだ無い。

## 利点と限界

### 利点

- **どこでも動く。** CPU だけ・55.1 MB・常駐 約 76 MB・1 件 0.07〜0.33 秒。GPU も、外への通信も、API の費用も要らない。商品文を外に送らない。
- **同じ入力には同じ答え。** LLM と違って、呼ぶたびに答えが揺れない。
- **迷いを隠さない。** 1 位だけでなく、確度・代わりの候補・「どこで迷っているか」の質問と、選択肢ごとの税率を返す。素材ひとつで税率が倍になるような所を、利用者に見せられる。質問に答えれば、10 桁の正解率は大きく上がる（テスト用の通販の商品名で、3 回までで 27% → 66%）。
- **版が分かる。** どの版の表で答えたかを必ず返し、表の改訂を毎日見張っている。
- **作り方を隠さない。** データの出どころ・加工・測り方・効かなかった試しまで書いてある。

### 限界

- **10 桁の 1 位は、そのまま申告に使える高さではない。** とくに、短い通販の商品名（テスト用で 10 桁 27%。作り始める前の目安の 30% に届いていない）。人の専門家は同じ種類の品で 95% と報告されている。
- **読み手を入れ替えても、テスト用の品での質問なしの精度は、v0.2.1 とほぼ同じだった。** 伸びたのは、学習よりあとに出た判例と、質問に答える流れ。
- 短い商品名には、10 桁を決める情報（素材・用途・大きさ）がそもそも書かれていないことが多い。質問か、項目の欄で補う前提。
- 確度は、通販の商品名と、品名だけの短い入力では高めに出る（テスト用の通販の商品名で、確度 0.7〜0.9 の品の 10 桁の的中率が 0.464）。確度 0.9 以上が付く品は少なく、その的中率は 0.86〜0.87。
- 判例に近い文の 6 桁は、公開の 6 桁モデルより低い（テスト用で 0.545 対 0.731）。
- 米国の HTS だけ。ほかの国の表には対応していない。
- 日本の税関の書き方の文は、過去の回答に似ていれば 6 桁で 60〜88% 当たるが、似た文の無い品では 42〜65%（[日本語での評価](#日本語での評価)）。品名だけ・品名＋概要では、v0.2.1 より 3〜5 ポイント低い。
- v0.2.x より遅い（1 件の時間が約 10 倍）。WebAssembly では、いちばん長い入力で 1 件 1 秒を超える。
- v0.3.0 は、読み手を入れ替えたので、同じ入力でも v0.2.x と答えが変わる。前の版の答えに合わせて作った仕組みは、入れ替える前に確かめ直すこと。
- 関税率表の注（部の注・類の注）と、通則の当てはめは、モデルが文として読んでいるわけではない。注で決まる品（袋物・部分品・セットなど）は間違えやすい。
- 税率は基本の欄だけ。
- ARM64 の実機では確かめていない。

物差しは、学習よりあとに出た判例（[新しい判例での評価](#新しい判例での評価)の確かめ用の半分。1,447 行・品名＋説明）の 10 桁の 1 位。開発用・テスト用の品は使っていない。比べる相手は、配っている形（0.419）か、その 1 つ前の形（0.414）。

| 学習の行の状態を覚えておき、近い実例の葉に点を足す（実例の記憶） | −0.005（混ぜる強さを入力ごとに変える形）・−0.020（強さを固定する形）。実例の少ない葉で下がる。採らない |
| いちばん紛らわしい誤りの節との間に余白を取る損失を、類・項の段に足す | ±0.000。採らない |
| 層を無くして、語のベクトルの平均で読む（6 層の読み手の出力を写した形） | 0.116。語の一致の点だけ（0.287）より低い。採らない |

v0.3.0 で効いたのは、土台を大きな学習済みモデルの先頭の層に替えたこと（0.280 → 0.419）と、質問の作り直しだった。質問なしの 10 桁は、学習の延長・データの追加・損失の工夫では、0.42 から動かなかった。

| `.github/workflows/` | 見張りの定期実行（版は毎日、公報は毎週） |

道具の自己確認:

```sh
python3 hts/rev_diff.py demo
python3 hts/rev_remap.py demo
python3 hts/bulletin.py demo
python3 hts/rev_remap.py check 2026HTSRev10 2026HTSRev11
python3 py/zeiban.py demo
```

### 見張りの細かい点

- 版の見張りは、現行の版が `releases/` にあれば何もしない。無ければ、現行の JSON を取って保存し、差分を書いてコミットする。取り逃がした版があれば、差分の `missed` に名前が残る。書式の印（`<i>` など）だけの違いは、変化に数えない。
- 公報の見張りは、まだ無い号を古い順に 2 号まで取り、PDF を文にして告示を抜き出す。取るのは、cbp.gov の robots.txt が禁じていない場所だけで、週 1 回・数回の要求にとどめる。
- 2025HTSBasic〜2026HTSRev21 の写しは、[Budget-Lab-Yale/tariff-rate-tracker](https://github.com/Budget-Lab-Yale/tariff-rate-tracker)（MIT、コミット a5ddf68）から、中身を変えずに置いた。2026HTSRev14 は無い。
