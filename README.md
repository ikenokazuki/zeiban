# zeiban（税番）

商品の文（品名・素材・説明）から、米国の関税率表（HTS）の 10 桁の番号を出す小さなモデル。CPU だけで動き、実行時に LLM もネットワークも使わない。

- **小さい・速い**: 配る一式は 57.5 MB、常駐メモリは最大 約 74 MB、1 件 5〜30 ms（CPU 2 スレッド）。
- **答えの形**: 10 桁のコード・確度・代わりの候補・基本の税率に、**確認の質問**（「綿か、ほかの繊維か」のように、候補が分かれる所を関税率表の公式の文で聞く）を付けて返す。
- **改訂に付いていく仕組み**: 関税率表の版を毎日見張り、版ごとの写しと差分を残している。モデルの中の表（木・行の文・税率）は重みではなくデータとして持つ。
- 英語と日本語の商品文を受け付ける。
- **動かし方は 2 つ**: Rust の実行ファイル（速い・小さい）と、Python と transformers の実装。答えは同じ。

> **先に知っておいてほしいこと**
>
> - 1 位の 10 桁を、そのまま申告に使える精度ではない。開発用の品での 1 位の正解率は、判例に近い文で 10 桁 46%・6 桁 68%、短い通販の商品名で 10 桁 26%・6 桁 38%。6 桁と確度を見て、10 桁は候補と質問で絞る使い方を想定している。
> - 下の数字は、どれも開発用（調整の途中で何度も見た品）での数。取り分けてあるテスト用は、まだ一度も採点していない。
> - 通関の判断の代わりにはならない。税率は関税率表の基本の欄で、追加の関税は入っていない。

## 使い方

動かし方は 2 つある。入力と応答の形は同じで、答えも同じになる。

- **Rust の実行ファイル**（下の 1〜3）: 速くて小さい。Rust で組み立てる。
- **Python と transformers**（[下の節](#python-と-transformers-で使う)）: 組み立てが要らない。エンコーダは、標準の ModernBERT の形で配っている。

### 1. 実行ファイルを作る

Rust が要る（1.91 で確かめた）。

```sh
git clone https://github.com/ikenokazuki/zeiban.git
cd zeiban/rs
cargo build --release
```

できるのは `rs/target/release/zeiban`（約 0.7 MB）。x86-64 の Linux で確かめた。AVX2 のある CPU では専用の計算を使い、無い CPU では素の Rust の計算に自動で切り替わる。ARM64 は、動く作りにはしてあるが、実機ではまだ確かめていない。

### 2. 一式を取る

重み・関税率表の木・索引などを 1 つにまとめたファイル（一式）と、その目録を、同じフォルダに置く。

```sh
mkdir -p ../bundle && cd ../bundle
curl -LO https://github.com/ikenokazuki/zeiban/releases/download/v0.1.0/zeiban.bin
curl -LO https://github.com/ikenokazuki/zeiban/releases/download/v0.1.0/zeiban.json
echo "ac8db43ec49dddfc91af6b546f413a43dee94cc918404db6da84c3dfd870e5a2  zeiban.bin" | sha256sum -c
```

### 3. 動かす

標準入力に 1 行 1 件の JSON を渡すと、標準出力に 1 行 1 件の JSON が返る。

```sh
echo '{"name": "Mens crew neck t-shirt"}' | ../rs/target/release/zeiban .
```

入力の欄:

| 欄 | 中身 |
|---|---|
| `name` | 品名（必須） |
| `material` | 素材（任意） |
| `categories` | 店の付けた分類。文か、文の並び（任意） |
| `description` | 説明（任意） |
| `prefix` | もう分かっている頭の桁。2・4・6・8・10 桁の数字（任意。下の「質問と呼び直し」） |

素材や分類は、説明の中に書くより、`material`・`categories` の欄で渡すほうがよく効く（品名のすぐ後に置かれるため）。入力は 256 トークンで切る。

応答（上の例。見やすく整えて、代わりの候補は 1 件だけ載せた）:

```json
{
  "hsCode": {
    "code": "6109901007",
    "description": "ARTICLES OF APPAREL AND CLOTHING ACCESSORIES, KNITTED OR CROCHETED > T-shirts, singlets, tank tops and similar garments, knitted or crocheted: > Of other textile materials: > Of man-made fibers > Men's or boys': > T-shirts: > Men's (638)"
  },
  "sixDigit": "610990",
  "confidenceScore": 0.51,
  "sixDigitConfidence": 0.68,
  "dutyRate": {
    "general": "32%",
    "special": "Free (AU,BH,CL,CO,IL,JO,KR,MA,OM,P,PA,PE,S,SG)",
    "other": "90%"
  },
  "alternates": [
    {"code": "6109901047", "description": "… > Thermal undershirts (652)", "probabilityMass": 0.158, "dutyRate": {"general": "32%", "special": "…", "other": "90%"}}
  ],
  "questions": [
    {
      "digits": 6,
      "ask": true,
      "confidence": 0.68,
      "options": [
        {"prefix": "610990", "label": "Of other textile materials:", "code": "6109901007", "probabilityMass": 0.87, "dutyRate": {"general": "32%", "special": "…", "other": "90%"}},
        {"prefix": "610910", "label": "Of cotton", "code": "6109100012", "probabilityMass": 0.13, "dutyRate": {"general": "16.5%", "special": "…", "other": "90%"}}
      ]
    }
  ],
  "htsRelease": "2026HTSRev22"
}
```

応答の欄:

| 欄 | 中身 |
|---|---|
| `hsCode` | 1 位の 10 桁と、関税率表の道筋の文 |
| `sixDigit` | 1 位の頭 6 桁（HS の国際共通の部分） |
| `confidenceScore` | 1 位の 10 桁が正しい確率の見積もり（0〜1） |
| `sixDigitConfidence` | 1 位の 6 桁までが正しい確率の見積もり |
| `dutyRate` | 関税率表の税率の欄。`general`（一般）・`special`（特恵）・`other`（第 2 欄）。公式の文字のまま |
| `alternates` | 代わりの候補（4 件まで）。`probabilityMass` は、上位 5 件の中での割合 |
| `questions` | 上位 5 件の頭の桁が分かれる最初の所の質問（0 か 1 個） |
| `htsRelease` | この一式が使っている関税率表の版 |
| `codes`・`scores` | 上位 5 件の 10 桁と点（照合用） |

実行ファイルの 2 つ目の引数に数を渡すと、上位の件数を変えられる（既定は 5）。

### 質問と呼び直し

品名だけでは決まらないとき、モデルは「どこで迷っているか」を質問として返す。

- `digits`: 質問の桁。上の例では 6 桁（綿か、ほかの繊維か）。
- `options`: 選択肢。`label` は関税率表の公式の文、`code` は「これを選んだらこのコードになる」、`dutyRate` はそのときの税率。選択肢を見せるだけで、税率の違いまで伝えられる。
- `ask`: 聞いたほうがよいかの目安。1 位の選択肢が正しい確率（`confidence`）が 0.7 より低いと `true`。
- 答えをもらったら、選ばれた選択肢の `prefix` を付けて呼び直す。その下の行だけから選び直す。

```sh
echo '{"name": "Mens crew neck t-shirt", "prefix": "610910"}' | ../rs/target/release/zeiban .
```

1 回の呼び出しで必ず答えが返り、実行ファイルは状態を持たない。質問は追加の欄なので、無視して 1 位だけを使ってもよい。

素材を最初から書けば、その質問は出ない。上の例に `"material": "100% cotton, knitted"` を足すと、6 桁は 610910（綿）に決まって税率は 16.5% になり、質問は 10 桁（肌着か、ふつうの T シャツか、など）に移る。

### 確度と税率の読み方

- `confidenceScore`・`sixDigitConfidence` は、判例に近い文とその書き直しで合わせ込んだ値。通販の商品名では、0.5〜0.7 の帯でまだ高めに出る（[確度の当たり具合](#確度の当たり具合)）。
- `probabilityMass` は候補の中での割合で、正しい確率ではない。
- `dutyRate` は関税率表の基本の欄だけ。第 99 類の追加の関税（232 条・301 条など）・不当廉売の関税・脚注・数量の単位は入らない。**実際に払う額ではない。**

### ほかの仕組みに組み込むとき

実行ファイルは、入力を 1 行読むごとに 1 行返す。立てたままにして 1 行ずつ渡せば、読み込み（約 12 ms）は最初の 1 回で済む。HTTP の口は入っていないので、要るなら薄い包みを自分で付ける。

### Python と transformers で使う

`py/zeiban.py` は、同じ一式を読む Python の実装。3 層のエンコーダを Hugging Face の transformers で読み、残り（語の一致の点・木の採点・確度・質問）を numpy で計算する。入力と応答は、Rust の実行ファイルと同じ。

```sh
pip install numpy torch transformers

# リポジトリの直下で。bundle/ は、上の「2. 一式を取る」で作ったもの
curl -LO https://github.com/ikenokazuki/zeiban/releases/download/v0.1.0/zeiban-encoder.tar.gz
echo "2eecca9fa8aa4755d51aea95d78070adb94eaea893661a7273fb8aef2f49ed63  zeiban-encoder.tar.gz" | sha256sum -c
tar xzf zeiban-encoder.tar.gz

echo '{"name": "Mens crew neck t-shirt"}' | python3 py/zeiban.py bundle zeiban-encoder
```

Python のコードから:

```python
import sys
sys.path.insert(0, 'py')
from zeiban import Zeiban

z = Zeiban('bundle', 'zeiban-encoder')
r = z.classify({'name': 'Mens crew neck t-shirt', 'material': '100% cotton, knitted'})
print(r['hsCode']['code'], r['sixDigit'], r['dutyRate']['general'])   # 6109100011 610910 16.5%
```

- `zeiban-encoder`（65.7 MB の tar.gz）は、エンコーダを「ふつうの 3 層の ModernBERT」の形（`config.json`・`model.safetensors`・`tokenizer.json`）で書き出したもの。重みは一式と同じ値（int8 に丸めた値を fp32 で持つ）なので、答えは Rust の実行ファイルと同じになる。公開の商品文 1,568 件と、質問に答えたあとの呼び直し 1,568 件で比べて、上位 5 件のコードと順・確度・質問・税率が全部同じだった（点の差は最大 0.00007）。
- 速さは 1 件 16〜22 ms（同じ台・2 スレッド）。読み込みに約 8 秒かかり、メモリは約 670 MB 使う（torch の分）。軽さが要るなら、Rust の実行ファイルを使う。
- 確かめた版: Python 3.11・transformers 4.57・torch 2.9（CPU）・numpy 2.4。

エンコーダだけを、transformers のふつうの呼び方で使うこともできる。

```python
import torch
from transformers import AutoModel, AutoTokenizer

tok = AutoTokenizer.from_pretrained('zeiban-encoder')
enc = AutoModel.from_pretrained('zeiban-encoder').eval()
with torch.no_grad():
    h = enc(**tok('title: Mens crew neck t-shirt', return_tensors='pt')).last_hidden_state[:, 0]   # 先頭トークンの状態 [1, 256]
```

このベクトルは、商品どうしの近さを測るための埋め込みではない（関税率表の節のベクトルと比べる前の、途中の値）。10 桁を出すには、`py/zeiban.py` のように、一式の射影・節のベクトル・索引と合わせて使う。標準の形なので、ModernBERT を読めるほかのエンジンにも載せられる見込みだが、確かめたのは transformers だけ。

## 精度

### 測り方

- **物差し**: 1 位のコードが正解と同じかを、10 桁と 6 桁で数える。
- **開発用の品**（調整の節目に使った品）:
  - 判例に近い文: ATLAS の検証用 200 品のうち、学習用にほぼ同じ文がある品を除いた 134 品。税関（CBP）の判例を LLM が要約した問い。
  - 短い通販の商品名: HSCodeComp（AliExpress の 632 品）から、結果を見る前に無作為に分けた 3 分の 1 の 210 品。
  - 日用品: OSS の Sora の HTS 推測の評価セットのうち、開発用の 52 品（正解は 6 桁）。
- **テスト用の品**（ATLAS のテスト用 200 品・HSCodeComp の残り 422 品・日用品の残り 98 品）は、最後に 1 回だけ採点するために取ってあり、まだ使っていない。
- 開発用の品は、モデルの形を選ぶ節目ごとに十数回採点に使った。下の数は、その分だけ楽観の側に寄っている可能性がある。
- 品の数が少ないので、数ポイントの差は違いと言えない（重みの乱数の種を替えるだけで、HSCodeComp の 10 桁は 0.06 ほど動く）。

### 同じ品で測った比べ（開発用）

| | 実行時に要るもの | 判例に近い文 10 桁 / 6 桁 | 通販の商品名 10 桁 / 6 桁 | 日用品 6 桁 |
|---|---|---|---|---|
| **zeiban v0.1.0** | CPU・57.5 MB | **0.463** / **0.679** | **0.262** / **0.381** | **0.923** |
| 〃 上位 5 件に正解が入る割合 | 〃 | 0.597 / 0.754 | 0.500 / 0.552 | 0.962 |
| 〃 質問 1 回に正しく答えたとき | 〃 | 0.537 / 0.754 | 0.386 / 0.495 | 0.962 |
| 語の一致の索引だけ（同じ材料・モデルなし） | CPU | 0.291 / 0.433 | 0.162 / 0.281 | 0.808 |
| 公開の 6 桁モデル（5.7 億パラメータ） | CPU で 1 件 0.2 秒 | — / 0.731 | — / 0.390 | 0.865 |
| LLM（Gemini Decision 1 に段ごとに選ばせる） | LLM の API | 0.299 / 0.500 | 0.524 / 0.638 | — |

- zeiban の行は、配る形（int8 の重み・Rust の実行ファイル）で測った。
- 「語の一致の索引だけ」は、zeiban の索引と同じ材料を BMX で引いて、一番近い行を答える形。16 通りの作り方から開発用で一番高いものを選んだので、高めに出ている。
- 公開の 6 桁モデルは `Kenpache/hs-code-classifier-en`（6 桁まで。10 桁は出さない）。学習データが公開されていないので、開発用と同じ出どころの文を学習している可能性を否定できない。
- LLM の行は、zeiban の学習データにラベルを付けた先生そのもの（[データの出どころと加工](#データの出どころと加工)）。関税率表の注は見せていない。
- 読み方: 判例に近い文では、zeiban は 6 桁で公開の 6 桁モデルに届かず、10 桁では先生の LLM を上回る。通販の商品名では、6 桁は 14 分の 1 の大きさで公開の 6 桁モデルと同じ高さだが、10 桁は LLM の半分。

### 公開されている数（品が違うので、直接は比べられない）

| 出典 | 仕組み | 品 | 10 桁 | 6 桁 |
|---|---|---|---|---|
| ATLAS（arXiv 2509.18400） | Atlas（LLaMA-3.3-70B を追加学習） | ATLAS のテスト用 200 品 | 40.0% | 57.5% |
| 同 | GPT-5-Thinking | 同 | 25.0% | 55.5% |
| 同 | Gemini-2.5-Pro-Thinking | 同 | 13.5% | 31.0% |
| HSCodeComp（arXiv 2510.19631） | 最良のエージェント | HSCodeComp 632 品 | 46.8% | — |
| 同 | 人の専門家 | 同 | 95.0% | — |
| arXiv 2605.14857 | LLM を 6 段で呼ぶ手順 | HSCodeComp | — | 64.2%（4 桁 75.0%） |

- zeiban の「判例に近い文 10 桁 0.463」は、ATLAS と同じ作りの品（検証用）での数で、Atlas の 40.0%（テスト用）と品が違う。上回ったとは言えない。同じテスト用での数は、1 回だけの採点のあとに書く。
- ATLAS の品は、正解のコードの 16% が現行の版の関税率表にもう無い（判例は古い版のコードで書かれている）。その分は、どのモデルも現行の表からは当てられない。
- 商用のサービスでは、Zonos・Avalara・Tarifflo などが 10 桁を返す。第三者の測定（arXiv 2412.14179。CBP の判例から作った 103 品）は 10 桁で Tarifflo 89%・Avalara（人手の分類）80%・Zonos 44% と報告しているが、著者の連絡先は評価された製品の 1 つと同じドメインで、品も少ない。zeiban を同じ品で測ったことは無い。
- 調べた範囲では、ここに挙げた 10 桁の仕組みは、どれも実行時に大きな LLM を使う。CPU だけで動く小さなモデルで 10 桁まで出し、公開の物差しで数を示したものは、見つからなかった（網羅的な調査ではない）。

### 質問に答えたときの伸び

上位 5 件が分かれる最初の所を質問にして、正しく答えたと仮定したときの 1 位の正解率（開発用）。

| 品 | 桁 | 質問なし | 1 回 | 2 回 | 3 回 |
|---|---|---|---|---|---|
| 判例に近い文 | 10 | 0.463 | 0.537 | 0.597 | 0.627 |
| 通販の商品名 | 10 | 0.262 | 0.386 | 0.495 | 0.552 |
| 通販の商品名 | 6 | 0.381 | 0.495 | 0.581 | 0.595 |

- 「正しく答えた」は上限の見積もり。利用者は、公式の文を読んでも選べないことがある。
- 最初の質問の選択肢に正しい答えが無い品が、判例に近い文で 22%、通販の商品名で 37% ある（上位 5 件に正解の側が入っていないとき）。
- `ask`（聞く目安）は、通販の商品名では約 8 割の品で `true` になる。短い商品名だけでは 10 桁が決まらないことが多いため。

### 確度の当たり具合

確度は、開発用とは別の行（判例に近い文 824 行と、判例の書き直し 5,060 行）で合わせ込んだ。その行での、交差検証の結果:

| 行 | 桁 | 確度 0.9 以上の行の正解率（合わせ込みの前 → 後） | 見積もりと実際のずれ（ECE。前 → 後） |
|---|---|---|---|
| 判例に近い文 | 10 | 0.764（89 行）→ 1.000（24 行） | 0.120 → 0.060 |
| 判例の書き直し | 10 | 0.851（935 行）→ 0.902（307 行） | 0.071 → 0.038 |
| 判例に近い文 | 6 | 0.786（369 行）→ 0.947（75 行） | 0.229 → 0.057 |
| 判例の書き直し | 6 | 0.843（2,784 行）→ 0.941（812 行） | 0.167 → 0.022 |

- 合わせ込んだあとは、高い確度が付く行は減るが、付いた行はよく当たる。
- 通販の商品名では、正解つきの行が開発用とテスト用にしか無いので、合わせ込みにも確かめにも使っていない。代わりの物差し（先生のラベルとの一致）では、0.5〜0.7 の帯で見積もりより当たりが低い。
- 開発用・テスト用での確度の当たり具合は、テスト用の採点のときに読む。

## 速さと大きさ

配る一式（v0.1.0）で測った。CPU は AMD EPYC（Milan）の仮想マシンで、計算は 2 スレッド。ほかの仕事も動いている台での数。

| 項目 | AVX2 の計算 | 素の Rust の計算（同じ台で強制） |
|---|---|---|
| 短い入力（64 トークン以下）の中央値 | 5.4〜6.4 ms | 12〜15 ms |
| 通販の商品文（中央値 55 トークン）の中央値・95% 点 | 8.4 ms・27 ms | 21 ms・79 ms |
| 256 トークンの入力の中央値・95% 点 | 26 ms・30 ms | 78 ms・92 ms |
| 読み込み（1 件目を受けられるまで） | 約 12 ms | 約 12〜18 ms |
| 常駐メモリの最大 | 74 MB | 74 MB |

| 一式の中身 | MB |
|---|---|
| 語の埋め込み（int8） | 26.6 |
| 語の一致の索引（BMX） | 12.3 |
| 節のベクトル（int8） | 9.9 |
| 3 層のエンコーダと射影（int8） | 3.5 |
| 語の区切りの表・NFKC の表 | 2.4 |
| 関税率表の行の文・木・税率 | 2.7 |
| **合計** | **57.5** |

1 件の時間には、語の区切り・索引の検索・エンコーダ・採点・上位 5 件の取り出しまでの全部が入る（JSON の読み書きは入らない）。一式はメモリにマップして読むので、常駐メモリのほとんどはファイルの写しで、実行ファイルが自分で持つ分は 約 12 MB。実行ファイルと、学習のときの Python の実装は、1,000 行で 1 位が全部同じになることを確かめてある。

上の表は Rust の実行ファイルの数。Python と transformers の実装は、1 件 16〜22 ms・メモリ 約 670 MB（[Python と transformers で使う](#python-と-transformers-で使う)）。

## モデルの作り

```
商品の文（品名・素材・分類・説明）
   │
   ├─(1) 語の一致の道 ─ BMX の索引（葉 19,926 個の文書）─→ 上位 64 個の葉と点
   │
   └─(2) 意味の道 ─ 語の区切り（最大 256 トークン）
                    → 3 層のエンコーダ（幅 256）→ 先頭トークンの状態 h
                    → 5 段の問いのベクトル q_t（2・4・6・8・10 桁）
                    → 節のベクトル e_t との cos
   ▼
(3) 段ごとの点   s_t = scale_t × cos(q_t, e_t) + λ_t × BMX_t
(4) 葉の点       = 5 段の log softmax(s_t) を、その葉の道筋に沿って足したもの
   ▼
上位 5 件の 10 桁 → 確度・質問・税率を付けて返す
```

関税率表は、類（2 桁）→ 項（4 桁）→ 号（6 桁）→ 8 桁 → 10 桁の木になっている。ここでは、木の分かれ目を「節」、一番下の 10 桁の行を「葉」と呼ぶ。木を 1 段ずつ下りるのではなく、5 段を 1 回で採点して、道筋の点の合計で葉を選ぶ。上の段で間違えても、下の段の点が強ければ取り戻せる。

| 部品 | 中身 |
|---|---|
| 語の埋め込み | 語彙 102,400 × 幅 256（ruri-v3 の語彙） |
| エンコーダ | ModernBERT の 3 層・幅 256・注意の頭 4・中間 1,024。層 0 は全体を見る注意、層 1・2 は近くだけを見る注意 |
| 問いの射影 | 段ごとの線形 256 → 256 が 5 つ |
| 節のベクトル | 木の節 38,276 個（段ごとに 96・1,228・5,612・11,414・19,926）× 幅 256。先に計算して配る |
| 語の一致の索引 | 葉ごとの文書（関税率表の道筋の文＋その葉の学習の文）を BMX で引く |

パラメータは合わせて 約 4,000 万個（語の埋め込み 2,620 万・節のベクトル 980 万・3 層と射影 約 350 万）。重みは全部 int8 で配る。

- **エンコーダ**: 土台は日本語の埋め込みモデル `cl-nagoya/ruri-v3-30m`（ModernBERT、10 層）。10 層を 3 つずつ平均して 3 層を作り、元の層との差を低ランクの差分（LoRA）で持たせてから学習する（Relaxed Recursive Transformers のやり方を、始めの値の作り方として使った）。学習のあとは差分を重みに畳むので、配る形は「ふつうの 3 層の ModernBERT」。
- **節のベクトル**: 節の文（関税率表のその節までの道筋の文）を同じエンコーダで読んだベクトルに、節ごとに覚えるベクトルを足したもの。文から作る部分があるので、行が増えても文さえあればベクトルを作れる。
- **BMX**: BM25 に、語の情報量（エントロピー）の重みを足した語の一致の式（arXiv 2408.06643）。関税率表は「綿」「ニット」「ステンレス」のような語がそのまま決め手になるので、語の一致の点を意味の点に足す。学習し直さずに語の一致の点だけを外すと、開発用の主な物差しは 0.333 → 0.210 に落ちた（古い重みでの測り）。
- **確度**: 段ごとに、上位 5 件の中で 1 位と同じ節にいる候補の割合と、1 位の点から、ロジスティック回帰で「1 位のその段までが正しい確率」を出す。質問に答えたあとの呼び直しには、別に合わせた係数を使う。
- **質問**: 上位 5 件の頭の桁が分かれる最初の段で、候補を節ごとにまとめて選択肢にする。

### 出どころ

| データ | 出どころ | ライセンス | 使い方 | 量 |
|---|---|---|---|---|

| 税関（CBP）の判例の原文 | Hugging Face の `orlandowhite/hts-cross-rulings` | データセットにライセンスの記載なし。判例そのものは米国政府の文書 | 原文から LLM が商品文に書き直したものだけを、学習と索引に | 書き直し 40,007 行 |

### 加工

1. **関税率表から木を作る。** USITC の JSON の字下げを積んで、類 → 項 → 号 → 8 桁 → 10 桁の木にする。第 98・99 類（特別な規定・追加の関税）は当てる対象から外す。税率は、葉の行か、税率の書いてある一番近い上の行から引く。
2. **判例から作った問い（ATLAS）。** 問いの決まり文句を外して商品の説明にする。正解のコードが現行の版に無いときは、残っている一番深い桁までを正解にする。コードが複数ある判例は、どれも正解として扱う。
3. **判例の原文を商品文に書き直す。** 判例の原文には、照会した人の名前や住所が入っている。そこで、原文から LLM が「通販の題名の形の短い品名」と「商品の説明」を英語と日本語で書き、名前・住所・会社名は書かせず、正規表現でも消す。正解のコードは、原文の決まり文句からこちらで抜き出し、データセットに付いているコードと食い違うものは使わない。原文そのものは、学習にも一式にも入れていない。
4. **合成の商品名を書いて、確かめる。** 葉ごとに、道筋・となりの行・関係する注を LLM に見せ、決め手（素材・性別など）を入れた商品名を書かせる。書いた商品名は、別の呼び出しで「この葉と近い葉のどれか」を選ばせ、元の葉に戻らないものを捨てる。397,180 題のうち 350,251 題（88%）を採用した。書き手も確かめ役も同じ LLM なので、同じ思い違いは通り抜ける。
5. **通販の商品文にラベルを付ける。** 公開の商品文（題名・ブランド・分類・説明）を LLM に見せ、類 → 4 桁 → 6 桁 → 8 桁 → 10 桁と、段ごとに関税率表の選択肢から選ばせて、確率ごと記録する。**これは正解ではなく、先生の答え**（同じ先生の 10 桁の正解率は、開発用の通販の商品名で 52%）。そこで、確率の高い段までを固い正解にし、その先は確率で重みを付けて使う。
6. **漏れを防ぐ。**
   - ATLAS の検証用・テスト用と同じ判例らしい原文（コードが頭 8 桁で合い、語の重なりが大きいもの。1,720 件）は、書き直しから外した。
   - ATLAS のデータセットは、学習用と検証用・テスト用に、ほぼ同じ文の組がある（検証用 200 品のうち 66 品）。そこで、検証用は重複を除いた 134 品で読む。
   - LLM への依頼には、開発用の正解・テスト用の品・判例の原文を入れていない。
   - 測る前に、何を比べて、どうなったら採用するかを決めてから測った。
7. **一式にまとめる。** 重みを int8 にし、節のベクトル・索引・木・行の文・税率と一緒に 1 つのファイルにする。

### 配っていないもの

- 学習データそのもの（判例の書き直し・合成の商品名・ラベルを付けた商品文）と、学習・データ作りの台本は、このリポジトリに入れていない。入っているのは、実行ファイルのソース・Python の実装と、一式・エンコーダのファイル（リリースの添付）。
- 判例の原文と、要約の文は配らない。

## 改訂への追従

関税率表は、よく変わる。2025 年は 33 回、2026 年は 11 月半ばまでに 24 回、版が出た。古い判例のコードは、いまの表にもう無いことが多い（2000〜2025 年の判例 5.5 万件の 10 桁のうち、現行の版に残るのは 41%）。学習したコードを重みに焼き付けるだけのモデルは、表が変わるたびに古くなる。

### いま動いているもの

- **版の見張り**（`.github/workflows/watch.yml`、毎日）: USITC の版の一覧を見て、新しい版が出ていたら JSON を保存し、前の版との差分を作る。過去の版の JSON はあとから配布元で取れないので、取り逃がさないことに意味がある。
- **版の写しと差分**（`releases/`・`diffs/`）: 2025 年の基本版から現行までの 56 版と、となり合う 55 組の差分。
- **型分け**: 差分を 3 つの型に分け、商品の行が変わったとき（B・C）は issue を立てる。

  | 型 | 条件 | 55 組のうち |
  |---|---|---|
  | A | 商品の葉（第 1〜97 類）の増減が無く、文も変わらない | 44 |
  | B | 文の変化だけ、または葉の増減が 40 未満 | 8 |
  | C | 葉の増減が 40 以上 | 3 |

  行が大きく動くのは年 2 回（1 月と 7 月）で、多くは 1 つの行が数行に分かれる形。
- **正解の付け替え**（`hts/rev_remap.py`）: 古い版の 10 桁を、新しい版の木に付け替える。番号だけ替わった行は新しい番号へ、分かれた・まとめられた・消えた行は、残っている一番深い桁までに直す。2025 年の基本版から 2026 年の Rev23 までの 55 回を通すと、葉 19,708 のうち 19,525 が同じ 10 桁のまま、179 が 8 桁まで、4 が 6 桁までになる。
- **判例の取り消しの見張り**（`.github/workflows/bulletin.yml`、毎週）: 税関の週刊の公報から、判例の取り消し・変更の告示（判例番号・日付・代わりの判例・結論のコード）を抜き出す。判例の本文は残さない。

### モデルの側の備え

- 応答には、いつも表の版（`htsRelease`）が入る。
- 木・行の文・税率・索引は、重みではなくデータとして一式に入っている。行の文や税率だけが変わる改訂は、学習し直さずに一式を作り直せば済む作りにしてある。
- 節のベクトルは、行の文をエンコーダで読んだ部分を持つので、増えた行にも文からベクトルを作れる。

### まだできていないこと

- いまの一式は 2026HTSRev22 で作った。現行の Rev23 は商品の行が同じ（型 A）なので、コードはそのまま通用する。**行が変わる版が出たときに一式を作り直す手順は、まだ自動になっていない。**
- 増えた行は、節ごとに覚えるベクトルが無い分だけ弱くなる見込み（覚えるベクトルを全部外すと、調整用の正解率が 0.56 → 0.45 に下がった。古い重みでの測り）。
- 改訂を再現した試験（葉の一部を「まだ無い行」として隠して学習し、あとで学習なしで足して当たるかを測る）は、計画だけで、まだ測っていない。「改訂に強い」と言える数字は、まだ無い。

## 利点と限界

### 利点

- **どこでも動く。** CPU だけ・57.5 MB・常駐 74 MB・1 件 数 ms〜数十 ms。GPU も、外への通信も、API の費用も要らない。商品文を外に送らない。
- **同じ入力には同じ答え。** LLM と違って、呼ぶたびに答えが揺れない。
- **迷いを隠さない。** 1 位だけでなく、確度・代わりの候補・「どこで迷っているか」の質問と、選択肢ごとの税率を返す。素材ひとつで税率が倍になるような所を、利用者に見せられる。
- **版が分かる。** どの版の表で答えたかを必ず返し、表の改訂を毎日見張っている。
- **作り方を隠さない。** データの出どころ・加工・測り方・効かなかった試しまで書いてある。

### 限界

- **10 桁の 1 位は、そのまま申告に使える高さではない。** とくに、短い通販の商品名（10 桁 26%）。人の専門家は同じ種類の品で 95% と報告されている。
- 短い商品名には、10 桁を決める情報（素材・用途・大きさ）がそもそも書かれていないことが多い。質問か、項目の欄で補う前提。
- 確度は、通販の商品名では合わせ込みを確かめられていない。
- テスト用での数字が、まだ無い。
- 米国の HTS だけ。ほかの国の表には対応していない。日本語の入力は受け付けるが、日本語での精度は測っていない。
- 関税率表の注（部の注・類の注）と、通則の当てはめは、モデルが文として読んでいるわけではない。注で決まる品（袋物・部分品・セットなど）は間違えやすい。
- 税率は基本の欄だけ。
- ARM64 の実機では確かめていない。

## 試して入れなかったもの

どれも、測る前に採用の条件（主な物差しの差が正で、95% 区間の下が 0 より上）を決めてから測った。主な物差しは、開発用の「判例に近い文」と「通販の商品名」の 10 桁の正解率の平均。

| 試したこと | 結果（主な物差しの差。95% 区間） |
|---|---|
| 同じ 3 層を 5 周回す（Looped Transformer） | +0.013 [−0.014, +0.039]。違いは見えない。読む時間は 約 4.7 倍 |
| 土台の 10 層をそのまま使う | +0.013 [−0.025, +0.050]。違いは見えない |
| 類ごとの注を覚える記憶（Titans） | +0.002 [−0.003, +0.006]。違いは見えない。学習が自分で記憶の重みを 0 に寄せた |
| 上位 10 件を読み直して並べ替える段 | −0.025 [−0.045, −0.007]。下がった |
| 段ごとに、となりの行の文を読み比べて選ぶ形 | 判例に近い文の 10 桁で 0.433 → 0.298。下がった |
| 乱数の種を替えた 3 つのモデルの点を平均する | +0.007 [−0.024, +0.036]。違いは見えない |
| 通販の商品文を索引にも入れる | 違いは見えない |
| 通販の商品文を 1 万品 → 2.4 万品に増やす | 4 桁は上がったが、10 桁は動いたと言えない |

読み直す回数や層を増やしても、入力に無い情報は増えない。効いたのは、語の一致の点（BMX）・通販の商品文の学習データ・質問だった。

### 見張りの細かい点

- 版の見張りは、現行の版が `releases/` にあれば何もしない。無ければ、現行の JSON を取って保存し、差分を書いてコミットする。取り逃がした版があれば、差分の `missed` に名前が残る。書式の印（`<i>` など）だけの違いは、変化に数えない。
- 公報の見張りは、まだ無い号を古い順に 2 号まで取り、PDF を文にして告示を抜き出す。取るのは、cbp.gov の robots.txt が禁じていない場所だけで、週 1 回・数回の要求にとどめる。
